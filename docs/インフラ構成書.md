## 1. インフラ概要

### 設計方針

- AWS を中心としたクラウド構成で統一する
- EC2 で Next.js アプリを稼働、RDS で MySQL を管理、S3 で画像を保管
- 無料枠（Free Tier）の範囲内での運用を目指す（Secrets Managerのみ対象外、7節参照）
- インフラのコード管理は Terraform（`infra/terraform/`、Phase 6-Bで実装・2026-08-06 実際にapply済み）。`infra/terraform/README.md`にinit/plan/apply/destroy手順・事前確認チェックリスト・state保護方針・S3の保護復旧方針を記載

## 2. アーキテクチャ図

```
[ユーザー（ブラウザ）]
        ↕ HTTP（HTTPS非採用、後述）
[EC2（Next.js アプリ / Nginx + PM2）]
  ├── フロントエンド（App Router / RSC）
  └── バックエンド（Route Handlers）
        ↕ Prisma（TCP / SSL）
[RDS（MySQL）]
        ↕ AWS SDK（HTTPS）
[S3（画像ストレージ）]
        ↕ タイルAPI（HTTPS）
[Leaflet + OpenStreetMap（地図サービス、APIキー不要）]
```

## 4. サービス構成（本番）

### 4.1 EC2（アプリホスティング）

| 項目 | 内容 |
|------|------|
| 用途 | Next.js アプリのホスティング |
| インスタンスタイプ | t2.micro（Free Tier 対象） |
| OS | Amazon Linux 2023 |
| Webサーバー | Nginx（リバースプロキシ） |
| プロセス管理 | PM2 |
| デプロイ方式 | **確定：SSH手動デプロイ**（Terraform管理外）。`git pull`→`.env.local`組み立て（Secrets Manager経由）→`pnpm install`→`NODE_OPTIONS=--max-old-space-size=1536 pnpm build`（t2.microのRAM制約でヒープ上限引き上げが必須、実機確認済み）→`prisma migrate deploy`→PM2起動。詳細手順は`infra/terraform/README.md`参照。GitHub Actions等からの自動デプロイは導入していない |
| カスタムドメイン | 未採用（EC2の自動割当パブリックIPをそのまま使用） |
| HTTPS | **非採用（HTTP運用を明示的に受容、2026-07-26確定・2026-07-28再確定）**。独自ドメイン・Elastic IP・Let's Encryptによる正式なHTTPS化はコスト・作業量を理由に見送る。確認用アカウントは使い捨て前提とし、本番の個人情報・パスワードを使い回さないことをREADMEに明記する |
| リージョン | **確定：ap-northeast-1（東京）** |

### 4.2 RDS（MySQL）

| 項目 | 内容 |
|------|------|
| 用途 | MySQL データベースのホスティング |
| インスタンスクラス | db.t3.micro（Free Tier 対象） |
| エンジン | MySQL 8.0 |
| ストレージ | 20GB（gp2、Free Tier 対象）、保管時暗号化（`storage_encrypted = true`）有効 |
| バックアップ | **確定：自動バックアップ保持期間7日**（`backup_retention_period = 7`）。destroy時は最終スナップショットを必ず取得する運用（`infra/terraform/README.md`のdestroy runbook参照） |
| 接続方式 | Prisma 経由（`DATABASE_URL` 環境変数）。マスターパスワードはTerraform変数に持たせず、`manage_master_user_password`によりAWS Secrets Manager管理（下記5節参照） |
| SSL | RDS がデフォルトで提供 |
| マルチAZ | 不採用（コスト抑制のためシングルAZ。個人開発規模のため本番運用時の再検討は行わない） |

### 4.3 S3（画像ストレージ）

| 項目 | 内容 |
|------|------|
| 用途 | 投稿写真・プロフィール画像のストレージ |
| プラン | Free Tier（5GB ストレージ・月 20,000 GETリクエスト・2,000 PUTリクエスト） |
| アップロード方式 | サーバーサイドから AWS SDK（@aws-sdk/client-s3）を使用（実装済み：`src/lib/s3.ts`） |
| オブジェクトキー | `uploads/{ownerUserId}/{randomUUID}.{ext}`（所有者スコープ付き。他人のオブジェクトを誤って削除・上書きできないようキーにアップロード実行者のユーザーIDを含める） |
| アクセス制御 | バケットポリシーで公開読み取り設定（バケット自体の作成はPhase 6-Bで実施。バケットポリシー・Public Access Block設定は6-A本文「S3公開方式」参照） |
| 画像変換 | 未定（サムネイル生成等は実装時に検討） |
| オブジェクト削除 | 投稿削除・画像差し替え（差分削除）・アバター差し替え時に実装済み（`deleteOwnedObjectsByUrl`、ベストエフォート・DB操作成功後に実行）。削除直前に`findStillReferencedUrls`で他の投稿・アバターからまだ参照されていないかを確認し、参照が残っていれば削除しない（旅行プランからの画像引き継ぎ`presetImageUrl`等で同一S3オブジェクトが複数レコードから参照され得るための保護）。アップロード済みだが未参照のまま残る画像の定期クリーンアップは未実装（Phase 6-Bへ引き継ぎ。判定方法・猶予期間等は実装計画書 Phase 6-A本文参照） |
| **Phase 6-Aメモ（`remotePatterns`・CSP）** | **実装済み**：`next.config.ts` の `images.remotePatterns` と `CSP_REPORT_ONLY` の `img-src` は、`AWS_REGION`/`AWS_S3_BUCKET_NAME` から組み立てた自バケットのホスト名（`<bucket>.s3.<region>.amazonaws.com`）に両方とも限定するよう変更済み（`src/lib/s3-url.ts` の `getBucketHostname()` を両ファイルで共有し、絞り忘れを防ぐ構成）。両変数が未設定の場合（CIビルド等）はS3関連のエントリを単純に省略し、ビルド自体は成功する。**6-Bで実際にEC2上で本番ビルドを実行する際は、`AWS_REGION`/`AWS_S3_BUCKET_NAME` を必ずビルド実行環境へ設定すること**（設定漏れがあるとビルドは成功するが画像だけ表示されない、気づきにくい壊れ方をする） |

| `AWS_SECRET_ACCESS_KEY` | 原則未設定 | 用途は上記と同じ |

## 6. デプロイ手順

### 初回セットアップ（確定・実施済み。詳細コマンドは`infra/terraform/README.md`）

```bash
# 1. infra/terraform/ で terraform apply（EC2・RDS・S3・IAMを一括構築、user-dataで
#    Node.js 24・pnpm・nginx・PM2・git・jq・mariadbクライアントを自動インストール）

# 2. RDSに初回のみ tripdiary データベースを手動作成（db_nameをTerraformに持たせると
#    変更時にRDS再作成〔force replacement〕になるため、既存環境では未設定のまま運用）

# 3. Secrets ManagerからDBパスワードを取得し .env.local を組み立て（AUTH_SECRET等も生成）

# 4. アプリのビルド・マイグレーション・起動
pnpm install
NODE_OPTIONS='--max-old-space-size=1536' pnpm build   # t2.microのRAM制約でヒープ上限引き上げが必須
pnpm exec dotenv -e .env.local -- pnpm prisma migrate deploy   # Prisma CLIは.env.localを自動読込しないため明示指定
pm2 start node_modules/next/dist/bin/next --name tripdiary --interpreter node -- start -H 127.0.0.1
pm2 save
```

### 通常デプロイ

```bash
# SSHでEC2へ接続し、git pull → 上記4のビルド〜起動を再実行する（GitHub Actions等の自動デプロイは未導入）
```

## 8. セキュリティ方針

| 項目 | 方針 |
|------|------|
| パスワード | bcrypt（ソルトラウンド：12）でハッシュ化 |
| セッション | Auth.js JWT Strategy（HttpOnly Cookie に JWT を保存、DB への書き込みなし） |
| 環境変数 | .env.local はリポジトリにコミットしない（.gitignore で除外） |
| AWS IAM | S3 アクセス用に EC2 インスタンスへ IAM ロール（`uploads/*`限定の`s3:PutObject`/`s3:DeleteObject`のみを許可する最小権限ポリシー）をアタッチ。本番では IAM ユーザー・長期アクセスキーは使用しない |
| AWS IAM キー | 本番はIAMロールの一時credentialsを`@aws-sdk/client-s3`のデフォルトプロバイダチェーンが自動的に使用し、長期キーは発行しない。ローカル開発でのみ`.env.local`に一時的な認証情報を設定する場合があり、その場合もサーバーサイドのみで使用しクライアントに公開しない |
| S3 バケット | Public Access Block（`BlockPublicPolicy`/`RestrictPublicBuckets`のみ無効化、ACL関連は有効のまま維持）・バケットポリシー（`uploads/*`に限定した匿名`s3:GetObject`のみ許可）は6-A本文・4.3節で確定済み。**Terraformでの実構築・実機確認は6-Bで完了済み**（2026-08-06、実際に画像アップロード・表示・削除まで確認）。あわせてownership controls（`BucketOwnerEnforced`）・デフォルト暗号化（SSE-S3）・未完了マルチパートアップロードの1日自動中断ルールも導入済み |
| HTTPS | **非採用（HTTP運用、4.1節参照）** |
| セキュリティグループ | EC2：**80番は`app_public_cidr_blocks`変数で公開範囲を制御**（構築・検証中は運用者IPのみに限定し、公開阻止DoD完了後に別applyで`0.0.0.0/0`へ切り替える二段階公開方式。443は開放しない）、22番（SSH）は運用者IPのみ許可、3306（MySQL）は EC2 のSGからのみ許可 |
| CORS | 未定（実装時に検討） |
| レート制限 | 実装済み（Phase 5-D、`src/lib/rate-limit.ts`）。固定ウィンドウ方式のインメモリカウンタで、ログイン（メール単位5回/15分）・サインアップ（IPアドレス単位10回/時、`X-Forwarded-For`の最左値を採用）・画像アップロード（ユーザーID単位、投稿30回/時・アバター10回/時）に適用。**単一プロセス前提**（EC2 t2.micro 1台構成のPhase 6を想定）のため、複数インスタンスへスケールする場合はRedis等の外部ストアへの置き換えが必要。CI（`.github/workflows/ci.yml`の`e2e`ジョブ）・perf（`.env.perf`）では`DISABLE_RATE_LIMIT_FOR_TESTS="true"`により無効化（本番環境変数には絶対に設定しないこと。2026-07-29 GATE-03対応で`ENABLE_TEST_ENDPOINTS`〔`/api/test/cleanup`用〕から分離）。**6-Bで以下を追加実装・実機検証済み（GATE-20）**: (1) Nginxで`X-Forwarded-For`を`$remote_addr`により上書きする設定（appendしない）とし、偽装ヘッダーによるIPベース制限の回避を防止（本番EC2で偽装XFF付きサインアップリクエストにより実地確認済み）、(2) 保有バケット数の上限（`MAX_BUCKETS=5000`）と満了エントリのスイープを導入し、生きているバケットは追い出さず新規キーのみ拒否する方式（LRU追い出し方式は`login:${email}`等IPに基づかないキー設計と組み合わせるとブルートフォース対策の解除と等価になるため不採用） |
| セキュリティヘッダー | 実装済み（Phase 5-D、`next.config.ts`）。`X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy`を常時付与、`Strict-Transport-Security`は本番のみ付与するコードになっているが、**HTTPS非採用のためHTTP運用では実質無効**（ブラウザはHTTPS接続でのみHSTSヘッダーを解釈するため）。CSPは`Content-Security-Policy-Report-Only`で運用開始（App Routerのhydrationがnonceなしinline scriptを使うため、まず違反レポートを収集してから段階的にstrict化する方針） |

## 9. 監視・ロギング

| 項目 | 内容 |
|------|------|
| アプリログ | 構造化ログ（pino、Phase 2.5-C導入済み）。出力先はPM2ログ（`~/.pm2/logs/`）／標準出力。**CloudWatch Logsへの集約は見送り**（追加のコスト・複雑さがあるため6-Bのスコープに含めない。個人開発規模ではPM2ログの直接確認で十分と判断）。**代わりにPM2ログローテーション（`pm2-logrotate`）をuser-dataで導入済み**（`max_size=10M`・`retain=7`・`compress=true`。t2.microのディスク枯渇対策、GATE-35）。実際のディスク使用量・ログローテーション設定の反映は2026-08-07に実証済み（`df -h`で71%〔5.6G/8.0G〕、`pm2 conf pm2-logrotate`で`max_size=10M`・`retain=7`・`compress=true`を確認。詳細は9.5節運用ログ）。**NginxとアプリのrequestId連携（`$request_id`のヘッダー転送＋`log_format`変更）は今回導入しない**（CloudWatch等のログ集約基盤が無い現状では2つのログを横断検索する手段が無く、単一EC2規模ではSSHで両ログをgrepすれば切り分けが成立するため。ログ集約基盤を導入するタイミングで合わせて検討する。導入時は`src/lib/request-logging.ts`の`randomUUID()`固定生成箇所にヘッダー優先のフォールバック分岐が必要）。**ログイン失敗ログ（下記）に残る未認証者の入力メールアドレスの実質的な保持期間は、pm2-logrotateの`retain=7`（世代）で決まる** |
| アクセスログ | Phase 5-Dで正常系アクセスログ（`method`/`path`/`status`/`duration_ms`/`userId`/`requestId`）を全APIに追加済み（`src/lib/request-logging.ts`）。Phase 5-E後の是正で同一`requestId`を`handleApiError()`のエラーログにも付与し、アクセスログとエラーログを突き合わせ可能にした。出力先はアプリログと同じくpino経由。**`/api/health`はNginx/PM2から高頻度でポーリングされるため、アクセスログ出力・`auth()`呼び出しの両方から除外済み（GATE-35）**。**`handler`がthrowした場合も`status: 500`でアクセスログを1行残すtry/finally化を実施済み（GATE-23）** |
| 認証失敗ログ | `src/lib/auth.ts`の`authorizeCredentials`が、スキーマ不正・レート制限超過・認証情報不一致の3経路すべてで`logger.warn`を出力する（GATE-23）。IPアドレスは`getClientIp()`（Nginxが`X-Forwarded-For`を`$remote_addr`で上書き済みのため信頼できる）、パスワードそのものはログに含めない。**既知のスコープ限定**: ログイン試行のレート制限キーは`login:${email}`のみでIPベースではないため、単一IPから大量の別メールアドレスで試行する攻撃は制限されずログ出力のみ行われる。ログによる監視・検知の実現のみをスコープとし、IPベースのログイン試行制限の追加は見送っている |
| DB モニタリング | RDS のダッシュボードで確認 |
| ヘルスチェック | `GET /api/health`（Phase 5-D実装済み、DB疎通確認込み、認証不要）。**6-Bで実機確認済み**（Nginx経由・直接アクセス双方で200を確認）。Swagger（`/api-docs`）にも`Health`タグで登録済み |
| エラー監視 | 連携ポイントのみ実装済み（Phase 2.5-D、サーバー側 `src/lib/monitoring.ts`、クライアント側 `src/lib/monitoring-client.ts`）。`global-error.tsx` からクライアント側の送信口を呼び出す。実際のSaaS（Sentry想定）導入・DSN発行は未定（ユーザー確認後に実施）。詳細は `docs/ログ運用設計書.md` 4節参照 |

## 10. CI構成（GitHub Actions）

`.github/workflows/ci.yml` で、プッシュ・PR時に以下5ジョブを実行する。

| ジョブ | 内容 |
|--------|------|
| `lint` | ESLint |
| `typecheck` | `tsc --noEmit` |
| `build` | `pnpm install --frozen-lockfile` → `pnpm build`（Next.jsのビルド可否を検証。6-A2で`@node-rs/bcrypt`〔napi-rsのネイティブアドオン〕を導入したため新設） |
| `test` | Vitest（`mysql-test` コンテナで実DB検証）。カバレッジ閾値（Statements 85% / Branches 75% / Functions 78% / Lines 86%）を下回るとジョブが失敗する |
| `e2e` | Playwright E2E。`continue-on-error` は設定していないため失敗時はCI上に赤く表示される。一方でブランチ保護の必須ステータスチェックには含めていない（TimeLine方式。運用実績を見て今後必須化を判断する） |

ブランチ保護の必須ステータスチェックは `lint` / `typecheck` / `build` / `test` の4つ。`e2e` は非必須だが `continue-on-error: true` は使わず失敗を隠さない運用としている。

Playwrightブラウザのキャッシュは `actions/cache`（`pnpm-lock.yaml`キー）で保存し、OS依存ライブラリ（`libnss3`等）は毎回`playwright install-deps chromium`で導入、ブラウザ本体のみキャッシュ未取得時に取得する2段階方式（詳細は`docs/テスト設計書.md`参照）。
