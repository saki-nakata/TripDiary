## 0. 位置づけ

Phase 2.5-C（開発基盤整備）で導入した構造化ログの方針と、ログを使った運用監視・障害対応の考え方をまとめる。

同コース内の別課題 TimeLine（Spring Boot）で出された要件「構造化ログの作成（バックエンドのみ対象）＋ログの運用監視・障害対応を踏まえた設計書作成（監視項目・閾値はアプリ内容に即して設計、アラート設計自体は不要）」を、TripDiary（Next.js Route Handler）向けに翻訳したものである。

**対象範囲**: バックエンド（Route Handler / Service / Repository）のログのみ。フロントエンドのログ（ブラウザコンソール等）は対象外。
**対象外**: 実際のアラート発報設定（閾値監視ツールの具体的な設定作業）。本書はあくまで設計であり、Phase 3以降で機能が増えるたびに随時更新する前提。

## 1. 構造化ログ方針

### 1.1 使用ライブラリ

`pino`（開発時は `pino-pretty` で整形表示）。`src/lib/logger.ts` にsingletonとして実装。

### 1.2 ログレベル定義

| レベル | 用途 |
|---|---|
| `error` | 未捕捉の例外（500系）。スタックトレースを含む |
| `warn` | 想定内のエラー（4xx系: 404 NotFound / 403 Forbidden / 400 Validation / 409 Conflict / 429 RateLimit）。クライアント起因のため深刻度は低いが、頻発時は異常の兆候になり得る |
| `info` | 正常系を含む全リクエストのアクセスログ（`withRequestLogging()`、1.5節参照） |
| `debug` | 開発環境のデフォルトレベル。詳細なデバッグ情報 |

環境変数 `LOG_LEVEL` で上書き可能。未設定時は本番 `info` ／開発 `debug`。

### 1.3 出力項目

`src/lib/api-error.ts` の `handleApiError` を基本の差し込み口とし、以下を構造化フィールドとして出力する。`withRequestLogging()`で生成したリクエストコンテキストは`src/lib/request-context.ts`の`AsyncLocalStorage`で保持し、`handleApiError()`のエラーログにも同じ`requestId`/`method`/`path`を付与する。

**例外**：`src/lib/s3.ts`の`deleteOwnedObjectsByUrl`（S3オブジェクト削除、Phase 6-A）はベストエフォート方針のため失敗を内部で握りつぶし、`handleApiError`を経由しない。この場合も同じ`AsyncLocalStorage`から`getRequestContext()`で`requestId`/`method`/`path`を直接取得し、削除失敗ログ・パーシャル失敗ログ・所有者外/解析不能URLのスキップwarnログに付与することで、アクセスログとの突き合わせを可能にしている。

| フィールド | 内容 |
|---|---|
| `requestId` | リクエスト単位のUUID。アクセスログと同じ値を出力し、同一リクエストの突き合わせに使用する |
| `method` | HTTPメソッド |
| `path` | リクエストパス（クエリ文字列を除く） |
| `errorType` | エラークラス名（`UnauthorizedError` / `NotFoundError` / `ForbiddenError` / `ValidationError` / `ConflictError` / `RateLimitError` / 未分類は概要のみ） |
| `message` | エラーメッセージ（4xx系） |
| `details` | バリデーションエラーのフィールド単位詳細（`ValidationError` のみ） |
| `err` | 未捕捉例外（500系）のエラーオブジェクト一式（スタックトレース含む、pinoの `err` シリアライザを利用） |

### 1.4 出力先

現状は標準出力（開発: `pino-pretty` で整形、本番: PM2ログとして収集）。

`docs/インフラ構成書.md` では「アプリログ: PM2ログ／未定（CloudWatch等は実装時に検討）」とされている。本設計はその「未定」を埋めるものではなく、まず構造化ログの**中身**（何を出すか）を先に固めた段階。出力先をCloudWatch等の集約基盤に送る配線は、実際にPM2運用を始めるデプロイフェーズ（実装計画書 Phase 6）で改めて検討する。

### 1.5 アクセスログ（正常系レスポンスタイム、Phase 5-Dで追加）

`handleApiError` はエラー時のみログを出すため、正常系を含む全リクエストの完了ログを別途 `src/lib/request-logging.ts` の `withRequestLogging()` で出力する。`auth/[...nextauth]/route.ts`（NextAuthの`handlers`をそのまま再エクスポートする特殊ファイル）を除く全route.tsの `GET`/`POST`/`PUT`/`PATCH`/`DELETE` エクスポートをこのラッパーで包んでいる。

`withRequestLogging()` は`requestId`を生成した上で、`requestId`/`method`/`path`を`AsyncLocalStorage`へ格納してから元のRoute Handlerを実行する。これにより、Route Handler内で`handleApiError()`が呼ばれた場合も、エラーログにアクセスログと同じ`requestId`が出力される。

| フィールド | 内容 |
|---|---|
| `requestId` | リクエスト単位のUUID（`crypto.randomUUID()`）。同一リクエストのアクセスログとエラーログを突き合わせるキー |
| `method` | HTTPメソッド |
| `path` | リクエストパス（クエリ文字列を除く） |
| `status` | レスポンスのHTTPステータス |
| `duration_ms` | ハンドラの処理時間（ミリ秒） |
| `userId` | ログイン中ユーザーのID（未ログイン・取得不能時は`undefined`） |

`info`レベルで出力するため、本番環境（`LOG_LEVEL`未設定時は`info`）でも常時記録される。開発環境（デフォルト`debug`）ではより詳細なログと合わせて出力される。

## 2. 監視項目と閾値（TripDiaryのアプリ内容に即した設計）

閾値は暫定値。実際のトラフィック傾向を計測してから調整する前提（★実測値なしの仮設定）。

| 監視項目 | 説明 | 暫定閾値 | 関連エンドポイント |
|---|---|---|---|
| APIエラー率（5xx） | 未捕捉例外の発生率。バグや依存サービス障害の兆候 | 直近5分間で5%超 | 全API |
| 認証失敗率 | ログイン試行の失敗率。ブルートフォース攻撃の兆候にもなり得る | 同一IPから短時間（1分）に5回超の失敗 | `auth/[...nextauth]`, `auth/signup` |
| レート制限超過（429） | `RateLimitError`の発生率。ログイン（メール単位5回/15分）・サインアップ（IP単位10回/時）・アップロード（ユーザーID単位、`post`は30回/時・`avatar`は10回/時）で発生しうる。ブルートフォース攻撃や不正botの兆候 | 直近5分間で同一エンドポイントへの429が10件超 | `auth/signup`, `upload/post`, `upload/avatar`（ログインの429は`src/lib/auth.ts`の`authorize()`内、`RateLimitSignInError`としてNextAuthのエラーログ経由で確認） |
| バリデーションエラー率（400） | 特定エンドポイントで急増した場合、フロントとバックエンドのスキーマ不整合を疑う | 直近5分間で同一エンドポイントへの400が20%超 | 全API（特に `posts`, `posts/[id]/comments`, `plans`） |
| 画像アップロード失敗率 | S3への`PutObject`失敗（設定不備・権限不足・S3障害等）の間接指標。`src/lib/s3.ts`の`uploadObject`が投げる例外は`handleApiError`の未分類エラーとして`logger.error`にスタック込みでログされる | 直近5分間で10%超 | `upload/post`, `upload/avatar` |
| S3オブジェクト削除失敗 | 投稿削除・画像差し替え・アバター差し替え時の`DeleteObjects`失敗（`s3.ts`の`deleteOwnedObjectsByUrl`が内部で捕捉し`logger.error`を出力。ベストエフォートのためリクエスト自体は失敗させない）。孤立オブジェクトが蓄積している兆候 | 発生したら検知対象（0件が正常。ただし例外ではなくログベースの監視） | `posts/[id]`（PUT/DELETE）, `users/[id]` |
| DB接続エラー | Prisma接続エラー（`PrismaClientKnownRequestError` の接続系コード等） | 発生したら即座に検知対象（0件が正常） | 全API（DB経由の処理） |
| DB疎通不能 | `/api/health`がDB疎通確認込みで503を返す状態。Phase 6のNginx/PM2ヘルスチェックからも参照する想定 | 発生したら即座に検知対象（0件が正常） | `/api/health` |
| レスポンスタイム悪化 | p95レイテンシの悪化。DB遅延やN+1の再発を検知。`withRequestLogging()`が全route.tsに`duration_ms`を出力するため、正常系も含めて計測できる（1.5節） | p95が平常時の3倍を超える | 特に一覧・集計系（`posts`, `posts/portal`, `posts/explore`, `plans`, `stats`）。`stats` はService層でJS側集計（1クエリ+メモリ内グルーピング）を行うため、投稿数の多いユーザーでの悪化を優先的に監視する |
| 他人リソースへの不正アクセス試行率（403） | 他ユーザーのプラン等への操作試行。総当たり的なID推測の兆候 | 直近5分間で同一IPからの403が10回超 | `plans/[id]`, `plans/[id]/complete` |

## 3. 障害対応フロー（インシデントレスポンス）

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  1. 検知    │ --> │ 2. 一次切り分け│ --> │  3. 対応    │ --> │ 4. 復旧確認 │ --> │ 5. 事後記録 │
└─────────────┘     └──────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
```

### 1. 検知
- ログ（`error`/`warn`レベル）から異常値を把握。現状は手動でログを確認する運用（自動アラートは本書のスコープ外）
- 2節の監視項目のいずれかが閾値を超えた場合を「異常」とみなす

### 2. 一次切り分け
- `errorType` で分類: `ValidationError`/`ConflictError`（クライアント起因、緊急度低） vs 未分類の500系（サーバー起因、緊急度高）
- 該当エンドポイント・発生時刻を特定し、直前のデプロイ・DBマイグレーションとの相関を確認

### 3. 対応（既知エラー分類ごとの初動）
| 分類 | 初動 |
|---|---|
| ValidationError急増 | フロントの入力チェックとバックエンドのZodスキーマの不整合を疑い、該当フォームを確認 |
| DB接続エラー | RDS/MySQLコンテナの稼働状況、コネクションプール枯渇を確認 |
| 500（未分類） | ログの `err.stack` からスタックトレースを特定し、該当コードを確認。再現手順があれば `docs/テスト設計書.md` に沿ってテストケースを追加 |
| 認証失敗率急増 | ブルートフォース攻撃の可能性。ログイン（メール単位5回/15分）で`RateLimitError`（429）が発動しているか確認 |
| 429（レート制限超過）急増 | 特定IP/ユーザーからの集中か、正規ユーザーの誤操作（連打等）かを`requestId`単位でアクセスログ・エラーログを突き合わせて切り分け。攻撃と判断した場合は`src/lib/rate-limit.ts`の閾値調整を検討（単一プロセス前提のインメモリ実装のため、複数インスタンスへのスケール時はRedis等への置き換えが必要、実装計画書 Phase 5-D 参照） |

### 4. 復旧確認
- 該当エンドポイントへの正常系リクエストが成功することを確認
- ログのエラー発生率が閾値内に戻ったことを確認

### 5. 事後記録
- 原因・対応内容・再発防止策を記録する（現状は決まった記録先がないため、当面はPR説明やコミットメッセージに残す。将来的に障害対応ログを一元管理する場所を検討）

## 4. エラー監視（Sentry等SaaS連携）の設計（Phase 2.5-D）

Phase 2.5-Dでは、Sentry等のエラー監視SaaSの**実導入は行わず、連携ポイントの実装と送信設計のみ**を行う。ログ（1〜3節）が「サーバーに残る記録を後から見に行く」ものであるのに対し、エラー監視SaaSは「本番でエラーが起きた瞬間に自動で検知・通知する」ものであり、両者は役割が異なる（4.4参照）。

### 4.1 実装済みの連携ポイント

| 層 | 場所 | 状態 |
|---|---|---|
| バックエンド | `src/lib/monitoring.ts` の `captureException()` を `src/lib/api-error.ts` の未捕捉例外（500系）パスから呼び出す | 実装済み（DSN未設定時は no-op） |
| フロントエンド | `src/app/global-error.tsx`（画面クラッシュ捕捉）から `src/lib/monitoring-client.ts` の `captureClientException()` を呼び出す | 実装済み（DSN未設定時は no-op。SDK実導入は未実施） |

サーバー側は `captureException()`、クライアント側は `captureClientException()` を差し込み口とし、監視SaaS導入時は各関数の中身を差し替えるだけで全体に反映される。

### 4.2 送信データの設計（送るもの／送らないもの）

| 送る | 送らない |
|---|---|
| エラーオブジェクト（スタックトレース） | リクエストボディの中身（投稿本文・コメント本文等の入力内容） |
| 発生箇所（`source`、例: `"api/posts POST"`） | パスワード・セッショントークン等の認証情報 |
| ログインユーザーの**IDのみ**（`userId`） | メールアドレス・ニックネーム等の個人を特定しうる情報 |

個人情報保護の観点から、ユーザーを一意に追跡するのに必要な最小限（ID）に留める。本文やメール等は送らない。

### 4.3 環境分離

- 送信の有無は環境変数 `SENTRY_DSN`（サーバー）／`NEXT_PUBLIC_SENTRY_DSN`（クライアント）の有無で切り替える
- **DSN未設定（開発環境・現状の本番）では送信しない**（`captureException` が即 return する no-op）。これにより開発中に余計な送信が発生せず、本番でDSNを設定した時点でのみ監視が有効になる
- DSNは `.env` に置き、`.env.sample` にキーだけ（値なし）を追記する（機密情報のコミット防止）

### 4.4 監視項目との役割分担（2節との対応）

エラー監視SaaS導入後、2節の監視項目のうち以下は「ログの手動確認」から「SaaSによる自動検知」へ移行できる。

| 2節の監視項目 | ログ（手動） | SaaS導入後（自動） |
|---|---|---|
| APIエラー率（5xx） | `error` ログを目視 | `captureException` 経由で自動通知・件数集計 |
| DB接続エラー | `error` ログを目視 | 同上（未捕捉例外として捕捉される） |
| 認証失敗率 / バリデーション400率 | `warn` ログを目視 | **SaaSには送らない**（4xxは送信対象外）ため引き続きログで確認 |
| レスポンスタイム悪化 | — | SaaSのパフォーマンス監視機能（APM）で計測（導入時に別途検討） |

つまり、SaaSは「サーバー起因の異常（5xx）の自動検知」を担い、クライアント起因（4xx）やレイテンシは引き続きログ／別手段で見る、という分担になる。

### 4.5 導入手順（将来、ユーザー確認後に実施）

1. Sentry等でアカウント作成 → Next.jsプロジェクトを登録し **DSN** を取得
2. `@sentry/nextjs` 等のSDKを導入し、`.env` に `SENTRY_DSN` / `NEXT_PUBLIC_SENTRY_DSN` を設定
3. `src/lib/monitoring.ts` の `captureException` にサーバー側の実送信処理を実装（4.2の送信データ設計に従う）
4. `src/lib/monitoring-client.ts` の `captureClientException` にクライアント側の実送信処理を実装
5. 意図的にエラーを発生させ、SaaSのダッシュボードに届くことを確認

※ アカウント作成・DSN発行は外部サービス契約を伴うため、自動では行わずユーザーの実施・確認を前提とする。

## 5. 今後の継続方針

- Phase 3/4/5で新規APIを追加する際、監視項目（2節の表）に該当する項目があれば追記する
- `path` / `userId` / `requestId` はPhase 5-Dで`withRequestLogging()`により全route.tsのアクセスログに自動付与済み（1.5節）。`requestId` / `method` / `path` はPhase 5-E後の是正で`handleApiError()`のエラーログにも付与済み。新規route.ts追加時もこのラッパーで包む運用を継続する
- ログ出力先のCloudWatch等への集約は、実装計画書 Phase 6（本番デプロイ）で検討する
