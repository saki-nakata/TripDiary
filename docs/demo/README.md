## README埋め込み時のトラブルと対応（重要、再撮影時も同じ手順が必要）

**GitHubのMarkdownレンダラーは、srcの値に関わらず`<video>`タグを一律で除去する**（`<details>`/`<summary>`/`<img>`は許可されるが`<video>`は非許可。レンダリング後のHTMLを`curl`で確認し`<video`要素が0件だったことで判明）。そのため、以下はいずれも**再生できない**:

- `<video src="docs/demo/xxx.mp4">`（リポジトリ内の相対パス）— タグごと除去される
- `<video src="https://raw.githubusercontent.com/...">`（絶対URLでも同様にタグごと除去される。仮にタグが残ったとしても`Content-Type: application/octet-stream`＋`nosniff`で配信されるため再生不可）
- `<video src="https://cdn.jsdelivr.net/gh/...">`（`Content-Type: video/mp4`で正しく配信されるが、そもそも`<video>`タグ自体が除去されるため無意味）

**唯一の正しい方法**: GitHubのuser-attachments機能を使う。Issue/PR本文の入力欄に動画ファイルをドラッグ&ドロップすると、`https://github.com/user-attachments/assets/<uuid>`という裸のURLが自動挿入される。このURLを`<video>`タグで囲まず、**Markdown中に裸のリンクとしてそのまま貼るだけ**でGitHub側が自動的にインラインの動画プレーヤー（実体は`https://private-user-images.githubusercontent.com/...`への署名付きURL）へ変換する。

再撮影・動画差し替え時の手順:
1. 新しい`.mp4`を`docs/demo/`に置く（既存ファイルを上書き、またはファイル名変更）
2. GitHub Issue作成画面（`/issues/new`）等の本文入力欄に動画をドラッグ&ドロップし、挿入された裸のURLをコピー（Issueを実際に送信する必要はない）
3. アップロード先のファイルサイズ（`curl --range 0-0`のレスポンスの`Content-Range`）をローカルの`.mp4`の実サイズと照合し、意図した順序・ファイルであることを確認する
4. READMEの該当箇所の裸URLを差し替える

## 動画から外した項目とその理由

参照動画（1機能をゆっくり見せる密度の単一フロー動画）との比較検討を経て、以下3項目は動画に含めず、README本文の説明文で補足する方針にした。

- **ドラッグ&ドロップでの画像並べ替え**: `dnd-kit`のPointerSensor/TouchSensorによる実装だが、撮り直しリスクの割に得るものが少ないと判断し見送り
- **費用内訳の入力**: 既に要素の多い②（投稿する）にこれ以上入力欄を足す価値が低いと判断
- **api-docs（Swagger UI）の表示**: 描画が重く、締めのカットとして弱いため見送り。README本文にリンクのみ記載

## ①（01-feed-engage）の再撮影・S3画像復旧（2026-08-09）

### 発覚した不具合

①の投稿詳細で画像2枚が真っ黒（実際は読み込み失敗のブロークン表示）になっていた。調査の結果、動画固有の問題ではなく**本番S3から一般投稿・デモ投稿用の画像実体が失われているサイト全体の不具合**と判明した。

- `seed-post-g-*`・`seed-post-demo-*`が参照するS3オブジェクトが軒並み`404 Not Found`（`GetObject`権限が無い匿名アクセスには`403`として見える）
- バケットポリシー・Public Access Block（`infra/terraform/s3.tf`）自体は正しく設定されており、権限設定の不具合ではなかった
- 無事だったのは`seed-confirm-user`（確認用アカウント、18件）と、②の実撮影で実際にアプリ経由でアップロードされた4件のみ
- `prisma/seed-production.ts`はDB投入前に`uploadObject()`でS3へ画像をアップロードする実装になっているが、投入後のどこかのタイミング（バケット再作成等）でS3側のオブジェクトのみ失われ、DBの`Image.url`は当時のまま残ったと推測される

### 復旧方法

`seed-production.ts`と同じ決定的ロジック（投稿ごとの著者・カテゴリ・画像枚数割り当て）で「本来あるべきS3キー」を再計算し、ローカルに残っていた`seed-images/`（Pexels取得プール）から、実際にS3へ存在しないキーだけを対象に同じキー名で再アップロードする一回限りのスクリプトを実行した。DBは一切変更していない（追記のみ）。116件を復旧（既存確認用18件はスキップ）。

### 再撮影

画像復旧後、`01-feed-engage.demo.spec.ts`を本番に対して再実行してmp4を差し替えた。いいね・行きたいはトグル方式のため、前回撮影分の状態が残ったまま再実行すると意図と逆方向にトグルされる。今回は事前に対象の状態を確認・調整した上で撮影し、最終的に前回撮影時と同じ状態（いいね・行きたいON、コメント1件）に揃えた。重複して作成されたコメントは`DELETE /api/comments/{id}`で削除済み。

なお、`行きたいに追加`ボタンは既に「行きたい」登録済みだと`title`が`行きたいを解除`に変わるため、`01-feed-engage.demo.spec.ts`のロケータを固定文言から正規表現（`/行きたい(に追加|を解除)/`）に変更し、今後同様の状態違いがあっても撮り直せるようにした。

## ⑤（05-mobile）の内容変更・高画質化（2026-08-09）

### 変更内容

- フローを「未ログインのモバイル表示→検索→投稿詳細→ログイン→下部ナビ長押し」から「未ログインのモバイル表示→ログイン→下部ナビ長押し→ライトモード→ダークモード切替」に変更（検索・投稿詳細の閲覧を削除し、末尾にテーマ切替を追加）
- ログイン方法を`context.addCookies()`によるstorageState注入から、下部ナビの「ログイン」リンク→実際のログインフォーム入力に変更した。`sessionStorage.setItem("justLoggedIn", "true")`（`login/page.tsx:37`）は実フォーム経由のログイン成功時にしか発火しないため、Cookie注入ではログイン直後のトースト案内「下のアイコンを長押しすると名前が表示されます」とボトムナビのバウンド演出（`Sidebar.tsx:112-124`）が撮影できていなかった。これらも見せるべき、という指摘を受けての変更
- テーマ切替はモバイル上部バーのアバターメニュー内`ThemeToggle`を使用し、`PATCH /api/me/theme`の200を待ってから`data-theme="dark"`を確認する形にした（04と同じ確認方法）
- ログイン・テーマ切替のいずれもDBへの書き込みを伴うため、`assertDemoWriteAllowed()`を呼ぶように変更（00〜04と同じ扱いにした）

### 画質改善

`playwright.config.ts`の`demo-mobile`プロジェクトは`video.size`に`devices["iPhone 13"].viewport`（390×844）をそのまま使っており、PC用動画（1280×720）よりネイティブ解像度が大幅に低いことが画質の悪さの原因だった。iPhone 13は実機のdevicePixelRatioが3倍のため、CSSビューポート・操作座標は変えずに`video.size`だけをアスペクト比を保ったまま2倍（780×1688）に拡大し、既にブラウザ側でレンダリングされている高精細な描画をそのまま活かす形にした。ファイルサイズは336KB→1.28MBに増えたが、依然として他の動画より小さい。
